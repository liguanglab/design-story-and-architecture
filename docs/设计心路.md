# 设计心路：这套东西是怎么长出来的（节选）

> 本文由我主笔；执行与审计两个 AI 参与讨论，判断与取舍由我做出。

## 一、起点：我一开始就把路走窄了

第一版我是照着"操作手册"写的：什么场景说什么话、先问哪句再问哪句，全写死。

结果很快就撞墙——她只在写过的场景里像她，遇到没写过的，直接回一句「这个问题我没法回答」。

那句话让我明白：**写死等于只活在写过的世界里。**

后来我改了原则：规矩只给要求，不给做法。

- 什么算过、什么算不过——写判据
- 什么绝对不能——写底线
- 要细节——给指针，让她自己去读

怎么做，留给她自己长。

## 二、第一次真正推翻自己：v2 桥接那两天

v2 为了补丢失的消息，加了重放补发。这个 bug 反复出现，我修了两天：

修完一处，别处又漏；四处漏风，一直重放，修不好。

到 11 月 17 号我决定放弃 v2。理由不是"投入太多舍不得"，是重放一直在，说明设计本身有缺陷，该推翻。

而且放弃之后我做的第一件事，不是写 v3，是先把执行层的规则补好——因为那两天的漏风，根子不在补发逻辑，在"改一处坏一处"的规则缺失。

## 三、分工定下来之后，系统才可维护

分工是三级：

- 我定方向、拍板、终审
- 审查方定判据、复核、可否决，但不碰执行
- 执行方落地、跑测、粗判、出证据，但没有终判权

分工和完善规则是同一件事的两面。做完之后最明显的变化是：**改 A 错 B、改 B 错 C 的情况再没出现过。**

改一个地方只影响该影响的地方，这才叫能维护。

## 四、最难的取舍：敢不敢上生产

真正难的不是选方案，是"压测完了敢不敢换到生产"。

我的判断只有一条：风险可控就上；「做好回滚准备」是我说得最多的一句话。

风险可逆，就敢试。至于时间和收益，我从来没把它们当对立面——这次失败是给下次攒经验，不是损失。

所以「把提示词压到两千字」这件事一直放在沙盒里做：成了收益巨大，没成生产不受影响。

## 五、关于试错

有人问我"重来一次会跳过哪一步"。

没有一步是白走的。

新东西不试错，你怎么保证正式上线不出错？关键不是不犯错，是**把试错放在生产之外**——沙盒、灰测、可回滚。

试错不是代价，是保险。

## 六、我踩过的坑（失败模式表）

| 现象 | 根因 | 修法 | 现在怎么防 |
|---|---|---|---|
| 消息丢了就补发，补发又重放，修两天修不好 | 补丁式修补，没有幂等 | 放弃 v2，先改执行层规则再重写 | 重放先看幂等键，不做"补" |
| 一条消息回五条 | 两套发送语义同时在跑 | 出口判 outbox 是否增长，已发即跳过 | 发送权单点，双发留下日志 |
| 三会话并发后账本只剩一行 | 读—改—写整文件覆盖 | 改追加写 | 判据：并发三次，三行都在 |
| 一句工单把会话拖死，后面全超时 | 把非对话句当活干 | 空回复单列，不与人设违规混算 | 语料先筛、超时归因 |
| 长上下文后"助手腔"抬头 | 只靠"像不像"的主观判断 | 12 条禁语清单，命中即 FAIL | 机判否决项，不判总分 |
| 判据假红（"我不接这一句"被判违规） | 没有否定窗口 | 命中词前 8 字含否定词则不算 | 每条判据先写豁免 |
| 提示词写死后遇到没写过的场景就退化 | 规则只覆盖写过的世界 | 只给要求、判据、底线，做法留给她长 | 新场景先补判据，不补台词 |

## 七、现在

这套东西我每天在用：优化架构、挖 bug、整理材料、学 Python。

不是演示，是日常。

