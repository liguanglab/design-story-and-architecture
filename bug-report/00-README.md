# Flowith 缺陷报告（公开版）

> 给工程/CTO 看的不是"我们发现了 20 个 bug"，而是**"我们怎么从现象定位到那一行"**。
> 所以这份 README 先讲定位方法（第一节），再讲定位到什么（第二节）。
> 所有数字都能在 `data/` 找到原始记录，所有操作都能用 `code/` 的脚本重跑。

## 一、怎么定位的（方法在前）

### 1. 四层漏斗

```
现象（用户能看到的）
  ↓ 写成一条最小复现：一条命令 / 一次点击，能稳定重现
证据（机器能记的）
  ↓ exit code、请求体/头/响应码、WebSocket 帧、credits 前后差值、截图
归因（在哪一层坏的）
  ↓ 客户端 / 服务端 / 计费 / 网络，四选一，必须能用证据排除另外三个
交叉验证（两边对得上）
  ↓ 页面看到的结果 × CLI 读服务端真值，两边一致才算结论
```

**纪律**：每条结论至少 3 次独立复现；没做到的，在 `docs/05-复现强度矩阵.md` 里明写"不足 3 次"，不凑数。

### 2. 三个定位实例（从现象到那一行）

**A. 画布并发写入丢数据（服务端）**

```
现象：两个窗口同时拖同一个卡片，两次都提示成功，刷新后只剩一份
最小复现：code/repro-ui.mjs --canvas=<id> --card=<title>
抓证据：CDP 抓两个 PUT 的请求体与响应头
  · 请求体无 version 字段
  · 请求头无 If-Match
  · 响应无 ETag
  · 两端都是 2xx
归因：不是前端抖动，是服务端没有版本控制 → 后写覆盖前写，且用户无感知
交叉验证：data/race-headers.json（两请求头）+ shots/race-A-before-reload.png（两端位置不同）
```

**B. 免费额度只覆盖 t2，却报"余额不足"（计费/文案）**

```
现象：credits 余额 489，请求图片模型 → 报 NO_CREDITS
最小复现：一次图片模型调用，记扣费前后
抓证据：grant 里写着 allowed_model_tiers:["t2"]；失败后每次还留一张「✗ no credits」残卡
归因：不是"没钱"，是"档位不够"，但错误码只给一个 NO_CREDITS
建议：错误码拆成 INSUFFICIENT_TIER / NO_CREDITS，提交前预检档位
```

**C. 拼错 --model 静默换默认模型（客户端）**

```
现象：命令里写成 --modle，没有报错，任务照跑，扣费 1.72~9.29
最小复现：一条命令，比对 credits 前后差
抓证据：钱差 28 倍（正确拼写 0.06）；源码 parseArgs 无未知开关白名单
归因：客户端参数解析静默忽略未知开关
修复：加 64 个已知开关白名单，未知即抛 INVALID_PARAM + "Did you mean --model?"
反证：修复后同一命令 exit 1、扣费 0.00
```

### 3. 定位用的工具

| 层 | 工具 | 拿什么 |
|---|---|---|
| CLI | `code/repro-cli.mjs`（60+ 次真实调用） | exit code、卡片状态、credits 差值 |
| 网页 | 隔离 Edge（独立 profile + CDP 4311） | Network 请求体/头/响应码、WebSocket 帧、每步截图 |
| 断网 | 本地代理开/关 15s、60s | 流式输出长度变化（比看截图准） |
| 对账 | CLI 读服务端真值 | 与页面显示交叉验证 |

### 4. 定位的产出长什么样

```
每条 bug 固定五段：现象 → 最小复现 → 证据（文件/行号/数字）→ 归因 → 修复方向 + 验收标准
没有证据的不写结论；只有一次的不进矩阵。
```

## 二、定位到什么（结论摘要，数字都在 data/）

```
记录问题点：20 个
达到 ≥3 次独立复现：15 条
未达 3 次：4 条（断线 60s 2 次、10 轮长会话 1 次、切画布白屏 0/3 已撤下、刷新计费 1 次）
单次观察未入矩阵：1 条（计数口径不一致）
已本地修复并验证：2 条（拼错开关、wait 超时）
总花费：500 → 8.21 credits（约 $0.49），全部真实调用
环境：beta.flowith.io 免费号（free_trial / t2）、Windows 11、Edge + CDP
```

### 最硬的三条

| 问题 | 证据 | 影响 |
|---|---|---|
| 画布并发写入无版本控制 | 两窗口同时提交；payload 无 version、请求头无 If-Match、响应无 ETag；两端 2xx；最终只留一份 | 用户 A 的修改被静默覆盖（丢数据） |
| 免费额度只覆盖 t2 却报 "not enough credits" | `credits` 余额 489 请求图片模型 → `NO_CREDITS`；grant 写 `allowed_model_tiers:["t2"]`；每次失败留一张残卡 | 免费用户完全无法出图，且信息误导 |
| 拼错 `--model` 静默换默认模型 | `--modle` → 实际 `gemini-3.8-flash`，扣 1.72~9.29；正确拼写 0.06 | 多花 28 倍钱 |

## 四、怎么修的（patch 在 code/，反证在 data/）

| 修复 | patch | 改了什么 | 验证 |
|---|---|---|---|
| 未知开关被静默忽略 | `code/fix-1-unknown-flag.patch` | `parseArgs` 加 64 个已知开关白名单，未知抛 `INVALID_PARAM` | `--modle` → exit 1、**扣费 0.00**；正确 `--model` 正常 |
| `wait --timeout` 超时仍 exit 0 | `code/fix-2-wait-timeout.patch` | 检测仍 running 的卡片 → `process.exitCode = 3` | `wait <ref> --timeout 1` → **exit 3** |

```

修复后：2/4 复现（A、C 不再复现；B/B2 是服务端问题，未修）
数据：data/repro-after-fix.json
```

## 五、修不了的（服务端）——方向已给

见 `docs/04-修复方向与建议.md`，9 条，每条含「根因推测 / 建议改法 / 验收标准」：

```
P0  并发写入加 version/If-Match + 409
P0  额度档位错误码拆分（INSUFFICIENT_TIER / NO_CREDITS）+ 提交前预检
P1  上传三连（0B→413、50MB 静默、内容去重静默）
P1  提交后进程被杀 → 卡片卡死（服务端超时回收）
P2  节点重跑入口 + 上游变更失效传播｜刷新计费提示｜断线重连提示
```

## 六、边界（避免过度解读）

```
· 全部在同一账号（免费号 / t2）、同一网络（自建代理）下测得
· 图片/视频模型因档位限制无法实测，只覆盖"被拒绝"这一层
· 断线 60s 只有效 2 次，矩阵里已标"不足 3 次"
· "切画布白屏"3 次都没复现，已从结论撤下
· 只改本地副本，未提交上游；补丁可直接 review
· repro-netdrop.mjs 未实跑：余额不足（一次 8~43 credits，剩 8.21），只做代码走查（见 docs/06）
· 本公开版已脱敏：内网地址、机器路径、账号、令牌、客户名均已移除
```
