# 自动化调用 canvas-cowork 时的三处语义不一致

> 一句话：这个 skill 在"参数、额度、任务状态"三处，**说的和做的不是一回事**。
> 三处都能稳定复现、都能指到源码行号、都有明确成本或行为后果。

| 项 | 内容 |
|---|---|
| 被测对象 | `flowith-ai/canvas-cowork`（Agent Skill，仓库 main，2026-11 拉取） |
| 运行环境 | Windows 11｜bun 1.4.5｜Flowith beta（免费号，`free_trial` 额度，`allowed_model_tiers: ["t2"]`） |
| 调用方式 | 脚本化 / CI 式非交互调用（`bun scripts/index.ts …`），共 60+ 次调用 |
| 证据 | 终端回显、卡片状态、`credits` 前后差值、源码行号；原始记录在 `<本地记录目录>` |
| 花费 | 全程约 12 credits（≈$0.012），其中定位窗口的 6 次试验约 0.3 credits |

---

## 一、参数层：说了"指定模型"，其实没生效（且更贵）

**现象**

```
$ bun scripts/index.ts text "…" --modle claude-haiku-5-5      # 注意拼错
Placed 1 text card (gemini-3.8-flash); writing…
exit=0                                   # 没有任何警告
```

**事实**

| 调用 | 实际模型 | 该次扣费 |
|---|---|---|
| `--modle claude-haiku-5-5`（拼错） | `gemini-3.8-flash`（默认） | **1.72 credits** |
| `--model claude-haiku-5-5`（正确） | `claude-haiku-5-5` | **0.06 credits** |

差价 **28 倍**（gemini-3.8-flash 标价 $0.75/$3.75 每 M tokens，haiku 是 $0.1/$0.5）。

**定位**

```
scripts/index.ts:111-131  parseArgs()
  任何 --name 一律塞进 flags Map，不校验是否为该命令认识的开关；
  各命令只读自己认识的键，未知键被静默忽略，不报错、不警告。
```

**复现率**：3/3（`--modle` / `--modl` / `--bogus`）。

**修复建议**
1. 各命令声明 `KNOWN_FLAGS`，`parseArgs` 遇到未知开关直接 `INVALID_PARAM`（可带"你是不是想写 --model"）；
2. 或命令结束时把"未被消费的开关"警告到 stderr。

## 二、额度层：说"钱不够"，其实是档位不允许（且失败留垃圾卡）

**现象**

```
$ bun scripts/index.ts credits
{"credits":489.49,
 "grants":[{"kind":"free_trial","left":489.49,
            "limits":{"allowed_model_tiers":["t2"]}}]}

$ bun scripts/index.ts image "一颗红苹果，白底" --model gpt-image-2.5-flare
Placed 1 image card (gpt-image-2.5-flare, ~6 credits); generating…
{"error":"NO_CREDITS","message":"…not enough credits or the plan doesn't include this model…"}
exit=1
```

**事实**

- 余额明明有 **489.49**，报的是 `NO_CREDITS`；
- 真实原因是免费额度只覆盖 **t2 档**，图片模型不在其中；
- 失败后画布上留下 **6 张** `✗ no credits` 的残卡（换 `sunburst` 模型同样）；
- 对照：文本模型（t2 档，`claude-haiku-5-5`）正常 `exit=0` 并正常扣费。

**定位**

- 错误语义：`NO_CREDITS` 同时承载了"余额不足"和"档位不允许"两种情况；
- 提交前只检查了"总余额 > 0"，没检查"该模型所需 tier 是否有额度"；
- 卡片是"先建占位、再异步生成"，失败路径没有清理占位卡。

**修复建议**
1. 错误码拆开：`INSUFFICIENT_TIER`（档位不允许）与 `NO_CREDITS`（真没钱）；
2. 提交前用 `grants[].limits.allowed_model_tiers` 做预检；
3. 失败时删除占位卡，或先预检再建卡。

## 三、任务层：说"还在跑"，其实既不能取消、超时还算成功

### 3.1 没有取消入口（3/3）

```
$ bun scripts/index.ts cancel 83cd46f8   → Unknown command "cancel"   exit=1
$ bun scripts/index.ts abort  …          → Unknown command "abort"    exit=1
$ bun scripts/index.ts stop   …          → Unknown command "stop"     exit=1
$ bun scripts/index.ts help              → 命令表里没有以上任何一项
```

但平台内部**是有 `cancelled` 状态的**：源码 `scripts/lib/tools.ts:238`
`if (task.status === "failed" || task.status === "cancelled")` —— 状态机支持取消，CLI 没有入口。

### 3.2 超时算成功（2/2）

```
$ bun scripts/index.ts wait 83cd46f8 --timeout 8
0/1 done
{ "cards":[{"ref":"83cd46f8","status":"running"}],
  "next":"Still generating: `wait 83cd46f8` later." }
exit=0        ← 超时了，但退出码是 0
```

代码位置：`scripts/index.ts:328-343`，`waitAndReport()` 把 `timeoutMs` 传给 `waitFor()`，
超时后照常走 `finish()` 输出，未把"超时"映射为非零退出码。

### 3.3 提交后 3~5 秒被杀 → 卡片卡死（4/4）

| 杀进程时机 | 卡片是否创建 | 120 秒后状态 |
|---|---|---|
| 2 秒（×2） | 没建卡（请求未发出） | — |
| **3 秒（×2）** | 建了（5 秒首现） | **running（卡死）** |
| **4 秒（×2）** | 建了（5 秒首现） | **running（卡死）** |

汇总：**卡死 4/6 ｜完成 0/6 ｜没建卡 2/6**。
窗口 = **提交之后、落账之前**（约 3~5 秒），不是"偶发"。

卡死之后的可选动作：

```
retry 83cd46f8  → {"error":"BUSY","message":"83cd46f8 is still generating: `wait 83cd46f8`."}
wait  83cd46f8  → 无 --timeout 时无限阻塞（实测 300 秒不返回）；有 --timeout 时 exit 0
delete 83cd46f8 → 能删掉（exit=0，6 张全部清理成功）
```

对照（这三条都能正常完成）：`--no-wait` 提交 ✓；生成中断网 20 秒 ✓；完成后 kill ✓。

### 3.4 关键措辞更正

```
不是"卡住无自愈路径"，而是：**有"删除"，没有"取消"**。
delete 能清场，但它是销毁——服务端之后算完，结果也一起丢。
所以用户手上是"一个会丢结果的假办法"，而不是"完全没有办法"。
```

### 修复建议

1. `wait` 超时 → 非零退出码（`TIMEOUT`），状态明确标 running；
2. 增加 `cancel <card>`：把卡片置为平台已有的 `cancelled` 状态；
3. `retry` 对"长时间 running"提供 `--force`；
4. 提交后立刻本地落一条"已提交待落账"记录，进程重启/被杀后可续（源码 retry 路径已有类似注释）。

## 四、三处为什么是"一条线"

```
参数层：说了"我指定了模型"    → 事实是默认模型
额度层：说了"钱不够"          → 事实是档位不够
任务层：说了"还在跑"          → 事实是既不能取消、超时也算成功
```

共同母题：**它陈述的状态与事实不一致**，而且三处都发生在"非交互、批量、自动化"的用法上——
这正是这个 skill 存在的意义所在。对交互用户，这三处几乎踩不到；对脚本用户，三处都会踩到。

## 附：给 issue 用的英文摘要

```
Title: Three state/reality mismatches when driving canvas-cowork from scripts

1) Unknown flags are silently ignored (scripts/index.ts:111-131):
   `--modle claude-haiku-5-5` runs with the default model
   (gemini-3.8-flash) and costs ~28x more (1.72 vs 0.06 credits). exit=0, no warning.

2) "NO_CREDITS" is used for tier rejections (free_trial grants are limited to
   allowed_model_tiers:["t2"]): `credits` shows 489.49 while image generation
   fails with "not enough credits", and each failure leaves a ✗ placeholder card
   on the canvas.

3) Task lifecycle has no cancel path (cancel/abort/stop → Unknown command; the
   platform still knows a "cancelled" status, tools.ts:238). `wait --timeout N`
   exits 0 while the card is still running. Killing the CLI 3–5s after submit
   strands the card in "running" (4/4 trials, 0/6 completions), retry answers BUSY,
   and `delete` is the only way out — it destroys the card, so a late result is lost.

All three are reproducible in non-interactive use; each has a minimal fix
(validate unknown flags / split error codes + pre-check tier / add cancel + non-zero
exit on wait timeout).
```
